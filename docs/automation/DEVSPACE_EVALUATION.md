# DevSpace Evaluation

Status: Sprint A8 feasibility study

Repository under review: `C:\AI\devspace`

Reference project: `C:\QuantTerminal`

Recommendation: **Prototype only**

DevSpace is a strong candidate for a future Developer Agent prototype, but it should not be adopted as the production Developer Agent until QuantTerminal adds a strict adapter boundary, command policy enforcement, worktree-first execution, and approval integration. DevSpace must remain a Developer Agent only. It must not replace Planner, QA, Screenshot, Review, State Store, or Approval.

## 1. How DevSpace Works

### Architecture

DevSpace is a self-hosted Streamable HTTP MCP server that exposes local coding capabilities to MCP-capable hosts such as ChatGPT or Claude.

Observed architecture:

- Express server with MCP transport in `src/server.ts`
- Single-user OAuth owner-token approval flow
- Workspace registry in `src/workspaces.ts`
- File/search/shell tools wrapped from `@earendil-works/pi-coding-agent` in `src/pi-tools.ts`
- Workspace session persistence through SQLite-backed state
- Optional ChatGPT Apps widget cards for file diffs and tool output
- Optional managed Git worktree mode

The mental model is remote access to explicitly approved local project folders.

### Local Workspace Access

DevSpace exposes an `open_workspace` tool. A client opens one workspace, receives a `workspaceId`, and then reuses that id for read, edit, write, shell, and review operations.

Workspace access is constrained by configured allowed roots:

- `DEVSPACE_ALLOWED_ROOTS`
- persisted config under `~/.devspace/config.json`

Path containment is implemented in `src/roots.ts` through resolved absolute paths and root containment checks.

### File Read/Write

File reads, writes, edits, grep, find, and directory listing are routed through `src/pi-tools.ts`.

Important behavior:

- `readFileTool()` resolves paths against workspace read roots.
- `writeFileTool()` and `editFileTool()` resolve paths against the workspace root.
- File tool path containment is enforced before invoking the underlying Pi coding-agent tools.
- Skill reads may be allowed outside the workspace only after skill activation rules allow it.

This is compatible with a Developer Agent role if the QuantTerminal adapter restricts allowed roots to a dedicated worktree or `C:\QuantTerminal` only.

### Terminal Command Execution

DevSpace exposes a shell tool named `bash` or `run_shell`, depending on tool naming configuration.

Important behavior:

- Shell commands run in the resolved workspace directory.
- Timeout defaults to 30 seconds and is capped at 300 seconds.
- The documentation explicitly says shell commands can do what the local user account can do.
- Filesystem containment applies to file tools, but shell commands are not a security boundary.

This is the largest risk for QuantTerminal automation. The Developer Agent adapter must enforce command allowlists before calling DevSpace shell tools.

### Approval Model

DevSpace uses a single-user OAuth owner-token approval model.

Observed controls:

- Owner password generated by `devspace init`
- Token stored in `~/.devspace/auth.json`
- OAuth access and refresh token TTLs
- Host header allowlist derived from local host and public base URL
- Optional tunnel/reverse-proxy deployment

This approval model grants access to the MCP session. It is not equivalent to QuantTerminal task approval, review approval, Telegram approval, or merge approval. QuantTerminal still needs its own Approval Agent and State Store.

### Git Behavior

DevSpace supports checkout mode and managed worktree mode.

Checkout mode:

- Opens the actual project directory.
- Edits apply directly to the active checkout.

Worktree mode:

- Creates a detached Git worktree under `~/.devspace/worktrees` by default.
- Requires a Git repository with at least one commit.
- Uses `git worktree add --detach`.
- Reports dirty source checkout state.
- Does not copy uncommitted source checkout changes into the worktree.

DevSpace also includes review checkpoint support:

- Creates internal Git refs under `refs/devspace/review/...`
- Captures working tree snapshots with temporary Git index files
- Produces aggregate diffs through `show_changes`

For QuantTerminal, worktree mode is required for any prototype. Checkout mode is too risky for automation.

### MCP Usage

DevSpace is an MCP server. It exposes tools including:

- `open_workspace`
- `read` / `read_file`
- `write` / `write_file`
- `edit` / `edit_file`
- `bash` / `run_shell`
- optional `grep`, `glob`, `ls`
- optional `show_changes`

Tool annotations mark write/edit/shell as destructive or open-world where appropriate. These annotations are useful but not sufficient as enforcement for QuantTerminal automation.

## 2. Fit With QuantTerminal Automation Layer

### automation/orchestrator

Fit: **partial**

DevSpace could serve as the future Codex Worker or Developer Agent executor behind the orchestrator's Codex stage. It should not own the pipeline.

Required adapter:

- Convert `TaskMessage` into DevSpace workspace operations.
- Open a dedicated worktree workspace.
- Apply edits through DevSpace edit/write tools.
- Run only approved validation commands.
- Return structured artifacts to the orchestrator.

The orchestrator should remain the caller and decision-maker.

### automation/contracts

Fit: **good with adapter**

DevSpace does not naturally emit QuantTerminal's A2 message contracts. An adapter can translate between:

- Planner task schema
- DevSpace workspace/edit/shell tool calls
- QA report schema
- Review handoff artifacts

DevSpace should not be allowed to invent new task schemas.

### automation/state

Fit: **must remain separate**

DevSpace has its own SQLite state for sessions, OAuth, and workspace metadata. QuantTerminal's Automation State Store must remain the source of truth for task status, pipeline state, approvals, and review outcomes.

DevSpace state should be treated as implementation detail, not orchestration truth.

### automation/qa

Fit: **do not replace**

DevSpace can run shell commands, but QuantTerminal's QA Harness already defines the canonical validation commands and report shape.

Safe integration model:

- Orchestrator invokes QA Harness directly.
- Developer Agent may run narrow local commands only when explicitly requested by the task.
- Final validation still comes from `automation/qa`.

### automation/screenshot

Fit: **do not replace**

DevSpace has no dedicated screenshot harness. It should not replace `automation/screenshot`.

If DevSpace is used as Developer Agent, screenshot capture remains a separate Screenshot Agent responsibility.

## 3. Risks

### Workspace Isolation

Risk: **medium**

File tools enforce workspace root containment, and allowed roots are configurable. However, broad allowed roots such as `C:\`, a home directory, or a parent folder containing many projects would create excessive access.

Mitigation:

- Configure only `C:\QuantTerminal` or a dedicated worktree root.
- Prefer DevSpace worktree mode.
- Reject checkout mode for automation.

### Command Safety

Risk: **high**

Shell commands run with local user permissions. DevSpace documentation explicitly warns that shell access can do what the user account can do.

Mitigation:

- QuantTerminal adapter must implement command allowlists.
- Disallow destructive commands by default.
- Disallow shell redirection and generated script writes.
- Route file modifications through edit/write tools only.
- Require Review/Approval before git push or merge.

### Accidental File Deletion

Risk: **high**

File tools are scoped, but shell can run destructive commands. Worktree mode reduces blast radius but is not a security boundary.

Mitigation:

- Use worktree mode.
- Disable or strictly wrap shell access.
- Block `rm`, `del`, recursive deletion, force checkout/reset, and broad move commands unless explicitly approved.
- Preserve QuantTerminal review and state records before destructive actions.

### Git Commit/Push Safety

Risk: **medium-high**

DevSpace can run git commands through shell and can create worktrees. Nothing observed prevents a model from committing or pushing if shell access is available and credentials exist.

Mitigation:

- Developer Agent must not commit, push, merge, or update refs directly.
- QuantTerminal Approval Agent must own approval.
- Future Auto Merge must be a separate controlled stage.
- Worktree refs and review checkpoints should not be treated as merge approval.

### Approval Requirements

Risk: **medium**

DevSpace OAuth approval authorizes a client to access the server. It does not approve individual tasks, file changes, validation outcomes, or merge operations.

Mitigation:

- Keep QuantTerminal Telegram Approval Agent.
- Store every task and approval in `automation/state`.
- Treat DevSpace access approval as transport authorization only.

### Windows Compatibility

Risk: **medium**

DevSpace supports Windows only with Git Bash, WSL, MSYS2, or Cygwin Bash. Native PowerShell and `cmd.exe` shell execution are not supported yet.

QuantTerminal currently uses Windows-oriented validation commands such as `npx.cmd`. DevSpace's Bash requirement may require command translation.

Mitigation:

- Prototype on WSL or Git Bash.
- Add command mapping for `npx.cmd` vs `npx`.
- Do not assume PowerShell behavior in DevSpace shell.

## 4. Recommendation

Recommendation: **Prototype only**

DevSpace is promising as a Developer Agent substrate because it already provides:

- MCP transport
- allowed-root workspace access
- file read/write/edit tools
- terminal execution
- project instruction loading
- skill discovery
- managed worktrees
- change review cards

However, it should not be adopted directly yet because:

- shell access is too broad for unsupervised automation
- OAuth approval is not task approval
- checkout mode can modify the active tree directly
- command safety needs a QuantTerminal-specific policy layer
- Windows command compatibility is not guaranteed
- DevSpace uses its own state and must not become the source of truth

## Fit Decision

Chosen option: **Prototype only**

DevSpace may be evaluated as:

```text
Planner
↓
QuantTerminal Orchestrator
↓
DevSpace Developer Agent Adapter
↓
QA Harness
↓
Screenshot Harness
↓
Review Agent
↓
Telegram Approval Agent
↓
State Store
```

DevSpace must not replace:

- Planner
- QA
- Screenshot
- Review
- State Store
- Approval

## Recommended Prototype Boundary

Prototype DevSpace only behind a Developer Agent adapter with these constraints:

1. Open `C:\QuantTerminal` in worktree mode only.
2. Use a narrow allowed root.
3. Disable direct commit/push/merge.
4. Allow only approved validation commands.
5. Apply file changes through edit/write tools only.
6. Return all outputs to QuantTerminal State Store.
7. Let QuantTerminal QA Harness run final validation.
8. Let QuantTerminal Review Agent decide pass/fail.
9. Let Telegram Approval Agent own human approval.
