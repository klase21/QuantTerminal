# QuantTerminal Research Renaissance Plan

Status: Product strategy  
Scope: Intelligence consumption and research workflow  
Planning horizon: 6-12 months  
Last updated: 2026-06-20

## 1. Research Vision

Research is QuantTerminal's primary workspace for developing a defensible understanding of a market situation.

It should help a user answer:

- What happened?
- Why did it happen?
- When did similar conditions occur?
- What happened after those conditions?
- Which evidence supports or contradicts the conclusion?
- How reliable is the conclusion?

Research is not a collection of feeds. It is not a larger Dashboard. It is not a generic charting page. It is a guided investigation that connects current observations to historical evidence and makes uncertainty visible.

### Dashboard and Research Serve Different Decisions

Dashboard provides immediate situational awareness.

Its job is to compress the current market into:

```text
Conclusion
  -> primary reasons
  -> concise evidence
  -> tactical attention
```

Dashboard should be fast, selective, and useful within seconds. It should not ask the user to inspect many cases, compare outcome horizons, or reason about conflicting evidence.

Research provides deep understanding and decision support.

Its job is to expand a selected market question into:

```text
Current state
  -> explanatory context
  -> historical comparisons
  -> forward outcomes
  -> evidence quality
  -> confidence and limits
```

Research may require deliberate interaction and manual historical loading. It must still remain responsive because it consumes prepared intelligence rather than computing history.

### Product Boundary

Research owns investigation and synthesis.

It should consume:

- current market-state summaries;
- narrative intelligence;
- information flow;
- prediction-market attention;
- Historical Analog V2 cache output;
- market-state features;
- exact outcome statistics;
- Replay links when verified coordinates exist;
- future Event Impact artifacts;
- future Market Memory artifacts.

Research should not:

- run historical searches;
- build market states;
- calculate outcomes;
- reconstruct Replay data;
- expose raw cache manifests as the primary experience;
- duplicate live verification already owned by Markets;
- duplicate execution planning already owned by Trade.

### Desired Research Outcome

A completed research session should produce a clear, bounded statement:

1. What the market is doing now.
2. Which forces appear most relevant.
3. Which historical cases are genuinely comparable.
4. What happened across multiple forward horizons.
5. Which evidence is strong, weak, missing, or contradictory.
6. How much confidence the evidence warrants.

Research should improve judgment without pretending to remove uncertainty.

## 2. Research User Journey

The ideal Research workflow is a single investigation with persistent context.

```text
Select Investigation Context
  -> Inspect Current Market State
  -> Review Narrative and Information Drivers
  -> Load Historical Context
  -> Compare Similar Cases
  -> Inspect Outcome Distribution
  -> Review Supporting and Contradicting Evidence
  -> Assess Confidence
  -> Continue to Replay, Markets, or Trade
```

### Step 1: Select Investigation Context

The user enters Research with a defined subject:

- symbol;
- exchange when relevant;
- interval;
- current-state timestamp or latest prepared state;
- optional source context such as Dashboard, Scanner, Markets, or Trade.

The context must remain stable throughout the investigation. A Historical Analog for BTCUSDT 1h must not be presented alongside narrative or outcome claims for an unrelated symbol or interval without explicit labeling.

Research defaults may provide a common market benchmark, but they must never silently substitute that benchmark for a requested symbol.

### Step 2: Establish the Current Market State

Research begins by describing the state being investigated:

- market direction or trend regime;
- recent returns;
- volatility;
- volume participation;
- distance from relevant moving averages;
- funding and open-interest features when available;
- state timestamp and source freshness.

This section answers:

> What exactly are we comparing?

It should use the current market-state representation already generated by Historical Analog V2 or a compatible prepared current-state source. Missing features remain missing.

### Step 3: Explain the Current Context

The user reviews real explanatory inputs:

- strongest narratives;
- regional narrative heat and divergence where available;
- prediction-market attention;
- macro and information-flow events;
- relevant live positioning or participation context.

This stage should distinguish observation from interpretation.

Examples:

- Observation: a narrative has the highest measured heat.
- Observation: a prediction market has high volume and a large probability change.
- Interpretation: these inputs may help explain current attention.

Research should not claim causality unless an intelligence system has measured it.

### Step 4: Load Historical Context Deliberately

Historical systems remain manual-load or cache-read only.

The user explicitly requests Historical Analog for the active symbol and interval. Research reads the prepared cache and returns:

- cache availability;
- current state;
- candidate count;
- ranked analogous cases;
- similarity scores;
- comparable feature count;
- generation time and source.

The interface must distinguish:

- not requested;
- loading;
- available;
- valid but no matching cases;
- cache missing;
- cache expired;
- cache incompatible;
- request failure.

Not requested is not the same as unavailable.

### Step 5: Compare Similar Cases

The user inspects cases as evidence, not as decorative cards.

For each case:

- timestamp;
- market regime;
- similarity score;
- comparable features;
- feature-level reasons for the match;
- 1h, 4h, 24h, and 7d outcomes;
- missing outcome windows;
- source and data coverage.

Selecting a case should update one shared case-detail view. The user should not need to mentally join disconnected summaries.

### Step 6: Evaluate Outcome Distribution

Research moves from individual examples to aggregate evidence:

- usable case count by horizon;
- average return;
- median return where calculable from cached cases;
- win rate;
- best case;
- worst case;
- dominant outcome;
- dispersion or range when available.

This stage answers:

> What usually happened next, and how variable were the results?

Average return alone is insufficient. A positive average with few cases or extreme dispersion must not be presented as strong evidence.

### Step 7: Review Evidence

Evidence should be organized into:

- supporting evidence;
- contradictory evidence;
- missing evidence;
- freshness and provenance.

Examples of supporting evidence:

- trend regime matched across high-similarity cases;
- volume and volatility profiles aligned;
- prediction-market attention supports the same current concern;
- outcome direction was consistent across usable cases.

Examples of contradictory evidence:

- current funding differs materially from analog cases;
- narrative conditions are stronger or weaker than the historical sample;
- 1h and 24h outcome distributions disagree;
- only a subset of features was comparable.

The system should never hide contradiction to preserve a cleaner conclusion.

### Step 8: Assess Confidence

Confidence should summarize evidence quality, not produce a recommendation.

It should be grounded in available fields such as:

- number of usable cases;
- similarity scores;
- comparable feature count;
- outcome consistency;
- source freshness;
- missing state features;
- agreement or disagreement between live and historical evidence;
- producer confidence when consuming an intelligence artifact.

Confidence should include a reason and limitation.

Example:

```text
Moderate confidence
Reason: 18 comparable cases with consistent 24h outcomes.
Limit: Funding history was unavailable for most cases.
```

No new confidence engine is required for the initial Research integration. Research should first expose the existing evidence needed to understand confidence.

### Step 9: Continue the Workflow

Research should provide purposeful exits:

- Open Markets to verify the live symbol.
- Open Replay for a selected historical case only when exact exchange, symbol, date, and hour coordinates exist.
- Open Trade when a current candidate already exists and the user wants execution planning.
- Return to the Historical Intelligence Explorer for a wider case-comparison view during the transition period.

Links must preserve investigation context. They must not replace explicit case coordinates with a default date or benchmark.

## 3. Existing Assets

### Historical Analog V2

Available intelligence:

- current market state;
- ranked historical cases;
- deterministic similarity;
- comparable feature count;
- exact forward outcomes;
- aggregate statistics;
- cache diagnostics.

Research role:

Historical Analog should provide the core answer to:

> What looked like this before?

Research should consume its cache-only API manually. It must not invoke the builder or duplicate similarity calculations.

### Historical Evidence

Available intelligence:

- similar case count;
- average return for prepared horizons;
- win rate;
- dominant outcome;
- source;
- generation time.

Research role:

Historical Evidence is a compact summary suitable for an investigation header or evidence overview. It should not replace detailed analog inspection.

Dashboard may show the compact evidence strip. Research should explain the cases and limitations behind it.

### Historical Intelligence Explorer

Available workflow:

- symbol and interval selection;
- current-state inspection;
- analog ranking;
- outcome summary by horizon;
- selected case detail;
- match-reason transparency;
- cache unavailability handling.

Research role:

The Explorer is the strongest current historical product workflow. Research Renaissance should reuse its interaction model and prepared data, not rebuild a separate historical system.

During transition, Research can deep-link to the Explorer with investigation context. Over time, the relevant Explorer workflow can become a Research mode or embedded workspace without changing the underlying intelligence contracts.

### Replay

Available intelligence and evidence:

- Binance kline price reconstruction;
- CryptoHFTData or fallback microstructure context;
- liquidations;
- open interest;
- funding;
- cached orderbook summaries where generated.

Research role:

Replay answers:

> What actually happened during this selected historical period?

Research should link to Replay from a verified historical case. Replay is evidence inspection, not case discovery. Research must not send incomplete case parameters that cause Replay to select an unrelated default window.

### Market States

Available fields:

- symbol and interval;
- timestamp;
- close;
- trend regime;
- 1h, 4h, and 24h returns;
- volume z-score;
- realized volatility;
- SMA distances;
- funding when supplied;
- open-interest change when supplied.

Research role:

Market state is the common vocabulary connecting current conditions and historical cases. It should anchor the investigation before narratives or analog outcomes are interpreted.

### Outcome Statistics

Available fields:

- case count by horizon;
- average return;
- win rate;
- best case;
- worst case;
- dominant outcome;
- exact case returns at 1h, 4h, 24h, and 7d.

Research role:

Outcome statistics answer:

> What happened next across the sample?

Research should present both aggregate and case-level outcomes. It should expose missing horizons and sample-size differences.

### Narrative Intelligence

Available fields include:

- narrative heatmap;
- top narratives;
- regional scores;
- article counts or aggregate heat;
- regional leaders;
- divergence score;
- generation time and source information.

Research role:

Narratives explain current attention and information concentration. They should be reviewed beside current state and prediction-market attention, not treated as historical causality.

### Prediction Markets

Available fields include:

- market title;
- probability;
- volume;
- liquidity;
- category;
- attention rank;
- source status.

Research role:

Prediction markets represent externally expressed expectations and attention. Research should distinguish probability, liquidity, and attention. A high probability in an illiquid market is not equivalent to high-confidence evidence.

### Information Flow

Available inputs currently combine:

- macro items;
- narrative updates;
- timestamps;
- source or signal labels.

Research role:

Information Flow should provide chronology and recency. It should help users understand which observations preceded or followed the current market state.

### Intelligence Artifact Registry

Available foundation:

- artifact schema;
- source and producer metadata;
- confidence;
- freshness;
- supporting evidence;
- subjects and tags;
- registry and reader interfaces.

Current limitation:

The registry is an in-memory reference implementation, and existing producers are not broadly publishing durable artifacts.

Research role:

The artifact model defines the desired long-term Research contract. It should not be treated as a production data source until publication and persistence are real. Phase 1 Research work should use existing cache-only routes and stable live APIs.

### How the Assets Work Together

```text
Current Market State
  -> defines the question

Narratives + Prediction Markets + Information Flow
  -> explain current attention and context

Historical Analog
  -> identifies comparable periods

Outcome Statistics
  -> measures what followed

Replay
  -> reconstructs a selected case

Historical Evidence
  -> compresses the conclusion

Artifact Model
  -> future common envelope for discovery, provenance, and reuse
```

No single asset is sufficient. Research creates value by preserving identity and provenance while moving through this chain.

## 4. Research Workspace Architecture

This section describes a product composition using existing foundations. It does not require new infrastructure.

### Investigation Context

Every Research session should have one shared context:

- symbol;
- exchange when relevant;
- interval;
- current-state timestamp;
- selected historical case;
- source route or initiating workflow.

All sections read from this context. Changing symbol or interval invalidates dependent historical selections but should not erase unrelated live data without a visible transition.

### Current State

Question:

> What is happening now?

Content:

- symbol and interval;
- state timestamp;
- trend regime;
- recent returns;
- volatility;
- volume state;
- funding and OI state when available;
- source freshness.

Behavior:

- visible first;
- lightweight;
- no historical load required;
- explicit missing features.

### Narrative Analysis

Question:

> Which information themes and expectations may explain current attention?

Content:

- strongest narratives;
- heat and article count;
- regional distribution and divergence;
- prediction-market attention;
- recent information-flow items.

Behavior:

- active independently of historical cache;
- no causality claims without measured Event Impact;
- each item retains source and update time.

### Historical Context

Question:

> Is prepared historical intelligence available for this exact state identity?

Content before manual load:

- Historical Context Available / Not Generated / Expired / Incompatible;
- generation time when known;
- Load Historical Context action.

Content after load:

- candidate count;
- analog count;
- source;
- cache generation time;
- schema version;
- current state used by the analog builder.

Behavior:

- manual read only;
- no auto polling;
- no auto build;
- cache diagnostics translated into user-relevant reasons.

### Similar Cases

Question:

> Which periods most closely resembled the current state?

Content:

- ranked case list;
- date and regime;
- similarity;
- comparable feature count;
- outcome values by horizon;
- selection state.

Behavior:

- selecting a case updates Case Detail, Supporting Evidence, and available Replay link;
- list order is the deterministic producer order;
- Research does not recalculate similarity.

### Case Detail

Question:

> Why was this case considered similar, and what happened?

Content:

- historical timestamp;
- historical state features;
- match reasons;
- 1h, 4h, 24h, and 7d outcomes;
- exact missing fields;
- verified Replay coordinates if available.

Behavior:

- no generic "Open Case" action without exchange, symbol, date, and hour;
- no fallback to latest Replay date;
- no benchmark substitution.

### Outcome Analysis

Question:

> What usually happened next?

Content:

- total and usable cases by horizon;
- average return;
- median return when derivable from the returned cases;
- win rate;
- best and worst case;
- dominant outcome;
- range or dispersion when existing data supports it.

Behavior:

- horizons remain separate;
- low case count is visible;
- missing returns are excluded and counted, not treated as zero;
- no prediction or trade recommendation.

### Supporting Evidence

Question:

> Why should we believe the conclusion?

Evidence groups:

- current-state evidence;
- historical-case evidence;
- outcome evidence;
- narrative evidence;
- prediction-market evidence;
- source references;
- contradictory or missing evidence.

Behavior:

- conclusion appears before detail;
- evidence is traceable to source and timestamp;
- contradictory evidence is first-class;
- raw cache paths and implementation objects remain hidden from normal users.

### Confidence

Question:

> How reliable is this conclusion?

Initial confidence presentation should use existing facts:

- case count;
- similarity;
- comparable features;
- outcome consistency;
- missing inputs;
- cache freshness;
- source provenance.

Research should present confidence as:

- level or producer score when available;
- reasons;
- limitations;
- freshness.

Research must not invent a combined confidence score before a deterministic confidence model and calibration process exist.

### Research Conclusion

Research may present a concise synthesis assembled only from loaded fields:

- strongest current theme;
- current market regime;
- historical dominant outcome;
- evidence strength;
- primary limitation.

This is deterministic formatting, not generated advice.

Example structure:

```text
Conclusion:
Current state is an uptrend with elevated narrative attention.

Historical evidence:
18 comparable cases; 24h outcomes were positive in 61% of usable cases.

Primary limitation:
Open-interest history was unavailable for most analog cases.
```

## 5. Research Page Audit

### Current Strengths

1. Research already owns the correct conceptual inputs: narratives, prediction markets, information flow, historical analogs, and Market Memory.
2. Live narratives and prediction markets load independently from historical systems.
3. Historical Analog and Market Memory auto polling are disabled, preserving responsiveness.
4. Manual historical requests use abortable, bounded fetches.
5. Real unavailable states are displayed instead of fabricated values.
6. The page uses a compact terminal presentation and does not require new visual foundations.
7. Historical Analog V2 is already adapted through a Research-specific cache-only route.
8. The separate Historical Intelligence Explorer demonstrates a stronger historical comparison workflow that can guide Research integration.

### Current Weaknesses

1. The page is organized as a sequence of panels rather than one investigation.
2. There is no shared symbol or interval context across live and historical sections.
3. Historical loaders are hardcoded to BTCUSDT and 1h.
4. Market Memory and Historical Explorer are presented as peer panels even though their production maturity differs.
5. The Research Brief can say "Unavailable" or "Manual load disabled" before the user has requested historical context, conflating not requested with no data.
6. The Research Summary reports historical systems as "Disabled" instead of updating after manual results load.
7. Historical case cards expose only a reduced adapter shape:
   - no similarity score as a typed field;
   - no comparable feature count;
   - no current market state;
   - no multi-horizon outcome detail;
   - no source freshness in the card.
8. Historical cases cannot open Replay because verified exchange/date/hour coordinates are absent.
9. Narrative Intelligence displays total heat but does not expose the full regional heatmap, regional leaders, or divergence already returned by the API.
10. Prediction Markets compress volume and liquidity into one fallback display, which can hide the distinction between attention and market depth.
11. Information Flow combines macro and narrative entries but does not establish a clear event chronology relative to the selected current state.
12. The page has no explicit supporting-versus-contradicting evidence model.
13. Confidence is implied through labels such as heat, attention, success rate, or outcome, but it is not explained.
14. Source, freshness, and schema diagnostics are inconsistent across panels.
15. Manual request controllers accumulate until unmount rather than being removed after completion. This is a small implementation concern for a later UI sprint, not a strategy blocker.

### Missing Capabilities

- Shared investigation identity.
- Current market-state anchor.
- Selected historical-case state.
- Feature-level similarity explanation.
- Multi-horizon aggregate outcome analysis.
- Contradictory evidence.
- Explicit confidence reasons and limitations.
- Verified case-to-Replay navigation.
- Consistent source and freshness display.
- A coherent research conclusion assembled from the active investigation.
- Artifact discovery once durable artifact publication exists.

### Duplicated Functionality

Research Historical Explorer and the standalone Historical Intelligence Explorer overlap in:

- analog loading;
- case listing;
- historical outcome display;
- unavailable handling.

The standalone Explorer currently has the richer implementation:

- current-state detail;
- similarity scores;
- comparable feature counts;
- outcome summary across four horizons;
- selected-case detail;
- transparent match reasons.

Research should not create a third analog presentation. It should reuse the Explorer's product model and existing cache response. The long-term choice should be one of:

1. Embed the Explorer workflow as a Research mode.
2. Keep the Explorer as a specialized destination and make Research preserve context when linking to it.

The first option provides the most coherent end-state, but it should be executed incrementally to avoid a UI rewrite.

Dashboard Historical Evidence is not duplicate functionality. Dashboard compresses prepared evidence; Research explains it.

Replay is not duplicate functionality. Research discovers and evaluates cases; Replay reconstructs one selected case.

### Honest Assessment

Research is useful as a live context board but incomplete as a decision-support workflow.

Its strongest live sources work. Its strongest historical workflow exists elsewhere. The central product task is therefore composition: connect current state, narratives, analogs, outcomes, evidence, and confidence around one investigation context.

## 6. Research Renaissance Roadmap

### Phase 1: Historical Analog Integration

Goal:

Make Research the natural entry point for cache-backed historical investigation.

Use existing:

- `/api/historical-analog`;
- `/api/research/historical-analogs`;
- Historical Intelligence Explorer interaction model;
- Historical Analog V2 cache;
- current market-state and outcome contracts.

Work:

1. Introduce shared symbol and interval investigation context.
2. Keep historical loading manual.
3. Replace the reduced historical card grid with:
   - current-state summary;
   - ranked case list;
   - selected-case detail;
   - outcome summary.
4. Distinguish not requested from unavailable.
5. Expose similarity, comparable features, source, generated time, and cache state.
6. Preserve a link to the standalone Explorer during migration.
7. Enable Replay only when verified coordinates exist.

Exit criteria:

- The user can investigate any covered symbol/interval cache.
- No history is computed during interaction.
- Current state and analog cases share one identity.
- Outcomes are visible by horizon.
- Cache absence remains explicit and non-blocking.

### Phase 2: Evidence-Centric Workflows

Goal:

Organize Research around conclusions, supporting evidence, contradictions, and limitations.

Use existing:

- narrative heatmap;
- prediction markets;
- information flow;
- Historical Analog cases and statistics;
- artifact evidence contract as a presentation model where useful.

Work:

1. Establish a Research Conclusion area based only on loaded real data.
2. Group evidence by source and kind.
3. Add contradictory and missing evidence sections.
4. Standardize provenance:
   - source;
   - observed/generated time;
   - freshness;
   - producer or schema version when relevant.
5. Make confidence transparent through existing evidence facts.
6. Preserve live usefulness when historical context is not loaded.

Exit criteria:

- Every conclusion is traceable to evidence.
- Missing evidence is visible.
- Conflicting signals are not suppressed.
- Research does not generate trade recommendations.

### Phase 3: Event Impact Engine

Goal:

Add measured answers to:

> What usually happened after this type of verified event?

Dependency:

Event Impact must first exist as a deterministic, cache-backed producer on canonical data. Research does not implement the engine.

Research integration:

- event identity and taxonomy;
- observed event time;
- source provenance;
- post-event outcomes at defined horizons;
- sample count and distribution;
- affected symbols;
- supporting historical cases;
- confidence and limitations.

Exit criteria:

- Only verified real events are displayed.
- Research consumes prepared Event Impact artifacts or cache output.
- No event-outcome calculation runs in Research.
- Narrative attention and measured event impact are clearly distinguished.

### Phase 4: Market Memory

Goal:

Add regime-level context beyond individual analog cases.

Dependency:

Market Memory must consume established market states and outcomes rather than duplicate them.

Research integration:

- matching regime or memory family;
- transition patterns;
- recurring outcome distribution;
- context features;
- case coverage;
- differences between current state and remembered regime.

Exit criteria:

- Market Memory adds a synthesis layer beyond Historical Analog.
- Regime definitions and versions are visible.
- No benchmark substitution occurs.
- Market Memory remains manual-load or artifact-read only.

### Phase 5: Research Artifact Ecosystem

Goal:

Allow Research to discover, compare, and inspect intelligence regardless of producer.

Dependency:

Historical Analog, Replay Intelligence, Event Impact, and Market Memory must publish durable artifacts through an operational registry. The current in-memory reference is insufficient for production Research.

Research integration:

- search by symbol, type, source, tag, confidence, and time;
- artifact summary list;
- selected artifact detail;
- evidence inspection;
- freshness and expiration;
- related artifact discovery;
- comparison across producers.

Exit criteria:

- Research consumers depend on artifact readers rather than implementation modules.
- Replacing a producer does not redesign Research.
- Artifacts retain source-specific metadata without exposing implementation internals.
- Expired or archived intelligence is clearly identified.

### Recommended Execution Order

The execution order should be:

1. Shared investigation context.
2. Historical Analog integration using the existing Explorer model.
3. Multi-horizon outcome and case-detail workflow.
4. Evidence and confidence presentation.
5. Verified Research-to-Replay context transfer.
6. Event Impact consumption after its producer exists.
7. Market Memory consumption after its producer exists.
8. Artifact discovery after durable publication exists.

This sequence improves the product using current assets before depending on future systems.

## 7. Anti Goals

Research should not:

- Add charts that do not answer a research question.
- Duplicate Dashboard's immediate summary layout.
- Duplicate Markets' live verification workspace.
- Duplicate Trade's execution-planning workflow.
- Treat Replay as a case-search engine.
- Expose raw cache paths, manifests, partitions, or provider payloads as the normal experience.
- Trigger builders, backfills, historical scans, or source downloads.
- Automatically poll heavy historical systems.
- Build a second Historical Analog engine.
- Build a second Market Memory implementation.
- Present mock or synthetic intelligence.
- Silently substitute BTCUSDT or another benchmark.
- Merge unrelated symbols, intervals, exchanges, or timestamps into one conclusion.
- Present narrative attention as measured causal impact.
- Present prediction probability without volume, liquidity, source, and freshness context.
- Convert average return into a trade recommendation.
- Hide low sample counts or missing outcome windows.
- Hide contradictory evidence.
- Invent a composite confidence score before its inputs and calibration are defined.
- Add infrastructure-heavy workflows to solve a product-composition problem.
- Create another permanent page for every intelligence producer.
- Require all data sources to succeed before Research becomes useful.

Research remains user-centric by asking a small number of clear questions and progressively revealing the evidence needed to answer them.

## 8. Success Metrics

Research Renaissance should be evaluated through measurable product and system outcomes.

### Faster Understanding

Measure:

- Median time from entering Research to identifying:
  - current market state;
  - strongest current narrative;
  - historical dominant outcome;
  - primary limitation.

Target:

- A covered investigation should communicate these four elements within two minutes without leaving Research.

### Better Decision Support

Measure:

- Percentage of completed investigations that include:
  - current-state review;
  - at least one selected analog case;
  - outcome summary review;
  - evidence or limitation review.

Target:

- More than 60% of historical Research sessions progress beyond the summary into case and outcome evidence.

### Reduced Information Overload

Measure:

- Number of unrelated top-level panels visible before an investigation context is selected.
- Number of repeated unavailable messages.
- User navigation steps required to connect an analog to its outcomes and evidence.

Target:

- One parent-level unavailable reason per missing historical source.
- Selected case, outcomes, and match reasons accessible without navigating among separate cards or pages.

### Increased Use of Historical Evidence

Measure:

- Manual Historical Context load rate.
- Analog case selection rate.
- Outcome-horizon inspection rate.
- Verified Replay open rate from selected cases.

Target:

- Historical context is intentionally loaded in a meaningful share of Research sessions rather than auto-requested and ignored.

### Evidence Traceability

Measure:

- Percentage of displayed conclusions with:
  - source;
  - generated or observed time;
  - supporting evidence;
  - explicit limitation when inputs are missing.

Target:

- 100% of historical conclusions.
- 100% of future artifact-driven conclusions.

### Confidence Transparency

Measure:

- Percentage of confidence displays that include reasons and limitations.
- Number of unlabeled decorative confidence scores.

Target:

- Zero confidence displays without provenance or explanation.

### Workflow Continuity

Measure:

- Percentage of Research-to-Replay links that preserve exact exchange, symbol, date, and hour.
- Percentage of route transitions that preserve symbol and interval context.

Target:

- 100% of enabled case links use verified coordinates.
- No silent fallback to a default Replay window.

### Responsiveness

Measure:

- Time to interactive for live Research sections.
- Historical manual-load response time.
- Navigation responsiveness while optional requests are active.

Target:

- Live Research remains usable without historical data.
- Historical requests never block navigation.
- No indefinite loading states.

### Data Integrity

Measure:

- Incidents of silent symbol substitution.
- Incidents of mock data reaching Research.
- Cases where missing outcomes are displayed as zero.
- Cases where stale intelligence lacks freshness labeling.

Target:

- Zero.

### Product Consolidation

Measure:

- Number of distinct Historical Analog presentations maintained.
- Percentage of Research historical behavior shared with the established Explorer model.

Target:

- One canonical case-comparison interaction model.
- Dashboard remains summary-only; Research and the Explorer own deep historical investigation.
